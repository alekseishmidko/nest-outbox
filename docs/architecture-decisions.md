# Архитектурные решения

## ADR-001. Стек проекта

Дата: 2026-07-28

Статус: принято.

## Контекст

Проект создается как учебное backend-приложение для тренировки SQL, транзакций, оптимизации запросов, паттерна Outbox без брокеров, observability и Docker-окружений.

Главная цель: писать и понимать SQL руками, а не прятать работу с БД за ORM.

## Решение

Используем следующий стек:

- Backend framework: `NestJS`.
- Runtime/package manager: `Bun`.
- База данных: `MySQL`.
- ORM: не используем.
- Доступ к БД: raw SQL через `mysql2`, connection pool и repository-слой.
- Миграции: SQL-файлы и migration runner без ORM.
- HTTP validation: `class-validator` и `class-transformer`.
- Env validation: `zod`.
- Seed: `@faker-js/faker` и кастомные seed-команды.
- Инфраструктура: `Docker Compose`.
- API-документация: `Swagger`.
- Логирование: `Pino`.
- Метрики: `Prometheus`.
- Визуализация: `Grafana`.
- Нагрузочное тестирование: `k6`.

## Почему без ORM

- Нужно тренировать `SELECT`, `JOIN`, `GROUP BY`, транзакции, индексы и `EXPLAIN`.
- Raw SQL лучше показывает реальную стоимость запросов.
- Проще демонстрировать Outbox как таблицу БД, а не как абстракцию ORM.
- Repository-слой сохранит модульность и не даст SQL смешаться с HTTP-кодом.

## Последствия

- Все SQL-запросы должны быть параметризованы.
- Запрещено собирать SQL через конкатенацию пользовательского ввода.
- Транзакции должны быть явно видны в коде.
- Для каждого сложного запроса нужно держать пример в документации.
- Для критичных запросов нужно сохранять `EXPLAIN` до и после оптимизации.

## ADR-002. Доступ к MySQL и миграции

Дата: 2026-07-28

Статус: принято.

## Контекст

Проект должен тренировать SQL напрямую: запросы, транзакции, индексы, блокировки, оптимизацию и Outbox на таблице БД. ORM намеренно не используется.

## Решение

Для доступа к MySQL используем `mysql2`.

Миграции реализуем через простой собственный migration runner на SQL-файлах:

- миграции хранятся в `database/migrations`;
- каждый файл содержит обычный MySQL SQL;
- примененные миграции фиксируются в таблице `schema_migrations`;
- runner выполняет только еще не примененные миграции;
- порядок выполнения определяется именем файла;
- миграции запускаются отдельной командой, например `bun run db:migrate`.

## Почему `mysql2`

- Поддерживает connection pool.
- Поддерживает prepared statements.
- Позволяет явно работать с транзакциями.
- Не навязывает ORM-модель и не скрывает SQL.

## Почему собственный runner

- Учебная цель проекта требует видеть SQL полностью.
- SQL-файлы проще анализировать через `EXPLAIN`.
- Меньше магии и зависимостей.
- Проще связать миграции с документацией по схеме БД.

## Ограничения

- Нужно аккуратно проектировать идемпотентность миграций.
- Нужно явно документировать порядок и назначение миграций.
- Автоматического rollback на первом этапе не делаем, чтобы не усложнять runner.

## ADR-003. Валидация данных

Дата: 2026-07-28

Статус: принято.

## Контекст

Приложению нужна валидация входных HTTP-данных, параметров окружения и данных перед выполнением raw SQL. Так как ORM не используется, границы валидации должны быть явными.

## Решение

Для HTTP DTO используем:

- `class-validator`;
- `class-transformer`;
- глобальный NestJS `ValidationPipe`.

Для env-переменных используем:

- `zod`.

## Правила

- Все публичные HTTP endpoints принимают DTO-классы.
- DTO-классы валидируются через `ValidationPipe`.
- Лишние поля должны отклоняться или удаляться на уровне pipe.
- Env-переменные валидируются до старта приложения.
- Repository-слой принимает уже проверенные значения и всегда использует prepared statements `mysql2`.

## Почему так

- `class-validator` и `class-transformer` хорошо интегрируются с NestJS и Swagger.
- `zod` удобен для проверки plain object-конфигурации окружения.
- Разделение HTTP validation и env validation оставляет код проще и понятнее.

## ADR-004. Качество кода и границы ответственности

Дата: 2026-08-03

Статус: принято.

## Контекст

Проект учебный, но код должен оставаться близким к production-подходу: строгая типизация, единый формат ошибок, предсказуемая валидация и понятные границы между HTTP, бизнес-логикой, SQL и background workers.

## Решение

- TypeScript работает в `strict` режиме.
- ESLint проверяет TypeScript-код, Prettier отвечает за форматирование.
- Глобальный `ValidationPipe` создается в `common/pipes`.
- Все HTTP-ошибки проходят через `ApiExceptionFilter`.
- DTO остаются на HTTP-границе.
- SQL-row типы не возвращаются наружу напрямую.
- Mapper-методы живут рядом с SQL в repository, пока нет повторяющейся сложной трансформации.

## SOLID

- Controller принимает HTTP-запрос и вызывает service.
- Service координирует бизнес-сценарий и не знает Express/Nest request object.
- Repository содержит SQL и не содержит HTTP-логику.
- Media generators не знают детали HTTP и возвращают результат генерации.
- Outbox worker занимается polling, блокировкой, retry и делегирует бизнес-обработку handler.

## KISS

- Не добавляем отдельный mapper-класс, пока преобразование `Row -> Record` локально и не повторяется.
- Не добавляем generic repository, потому что raw SQL должен оставаться видимым.
- Не выносим helper ради одного места использования.

## DRY

- Повторяющиеся DTO/query/helper-части выносятся только после реального повторения.
- Общие infrastructure-компоненты размещаются в `common`.
- Модульные типы остаются в `types` конкретного модуля.
